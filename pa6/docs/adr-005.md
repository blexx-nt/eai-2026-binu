# ADR-005 — Contract-first checkout with a sequential, compensating saga

**Status:** accepted
**Date:** 2026-11-02

## Context

POST /checkout has to turn four services I do not control (payment, inventory, shipping, notification) into one business transaction. The constraints that forced decisions:

- Only payment and inventory expose a compensating action (refund, release). Shipping and notification have none. If notification fails, shipping has already created a shipment; I still release inventory and refund payment, so a shipment can outlive a refunded order and nothing in the mocks lets me undo it.
- A call that has not answered within REQUEST_TIMEOUT_MS (2500 ms) must become 504 + timeout, while a non-2xx answer is a business failure that becomes 422 with the mock's own code. A timed-out call may in fact have succeeded downstream, and I cannot know.
- A second request with the same Idempotency-Key arriving while the first saga is still running reads an in_progress record. It needs its own answer (409 idempotency_conflict), not a hang and not a second saga run.
- The lint rules forced me to state things I would otherwise have left vague: every 4xx/5xx response needs an error schema, and every array needs maxItems. The canonical schema does not bound items, so the given validation would never enforce a bound that my contract promises.

## Decision

- Contract first. openapi.yaml was committed (lint clean) before any orchestrator code. It restates the canonical order, caps items at 50, defines one ErrorResponse and one SagaResult shared by 200/422/504, and documents the five outcomes.
- In server.ts the POST /checkout handler rejects more than 50 items (MAX_ITEMS, mirroring the contract) with 400 validation_error, after the header and canonical-schema checks.
- Idempotency: the handler looks up the key. A different payload hash gives 409 idempotency_payload_mismatch. A record still in_progress gives 409 idempotency_conflict. A finished record replays the stored HTTP status and body. The in_progress record is written synchronously before the first await, so check-and-claim has no gap inside one process. Results are written to the saga store and to the idempotency store (re-read first, so records written by other requests meanwhile are not overwritten).
- runSaga in saga.ts runs the four steps one at a time with await. callStep uses an AbortController with REQUEST_TIMEOUT_MS: an abort is a timeout, a non-2xx answer or a network error is a failure carrying the mock's code. Every call, compensations included, is appended to the trace with timestamps.
- On a failure at step k, runSaga walks the completed steps in reverse and calls only compensations that exist (inventory_release, then payment_refund). If one fails the result is 422 failed + compensation_failed. Otherwise the HTTP status follows the original failure (504 for timeout, 422 otherwise) and the status is failed if nothing had completed, else compensated.
- Money is summed as integer cents and formatted once as a two-digit decimal string (e.g. "63.90"), never through a float.

## Alternatives considered

- Compensating endpoints for shipping and notification on the mock services. This is the cleaner fix for the shipment-without-payment problem, but the mocks are fixed for this assignment, so I accepted the gap instead.
- Choreography, as in PA5, where each service reacts to an event. I rejected it for checkout because the caller needs one ordered, synchronous answer and something must decide "refund the payment because shipping failed". What I give up is that the orchestrator becomes a single point of failure that knows all four services.
- Calling independent services in parallel. Faster, but compensation order and the trace depend on strict sequencing, and the assignment requires it.
- Generating request validation from openapi.yaml as the single source of truth. I kept a hand-written MAX_ITEMS check instead, which means the bound lives in two places and can drift.

## Consequences

Easier: the outcome table maps one-to-one onto code paths, and a replay is a plain lookup.

Costs I accepted:

- A shipping or notification failure leaves a created shipment that cannot be cancelled.
- A step that timed out is not treated as completed, so it is not compensated; a payment that timed out may have been authorised and never refunded.
- If the orchestrator is killed mid-saga, the in_progress record stays and the same key gets 409 idempotency_conflict forever. There is no recovery.
- On an unexpected exception I delete the idempotency record so the caller can retry, but a retry can run the saga again after payment was already authorised (double-charge risk).
- Two requests for the same orderId with different keys can race; the saga store is keyed by orderId, so the last write wins.
- The stores are JSON files without locking, so this works for a single instance only. The request hash is over JSON.stringify of the body, so a reordered but identical payload counts as different.
- The 50-item bound is duplicated in the contract and in the code. Adding a fifth step means one more entry in the steps list and a higher maxItems for the trace in the contract.
