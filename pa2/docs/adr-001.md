# ADR-001 — Delivery guarantees between the order producer and the warehouse consumer

**Status:** accepted
**Date:** 2026-09-21

## Context

There are four decisions in this assignment, and each one has a version that looks fine until you actually break something.

**Durable queue.** I set `durable: true` when I declare the queue in both `connectProducerChannel` and `connectConsumerChannel`. I actually saw why this matters through demonstration (a) — the test publishes a message, runs `docker restart pa2-rabbitmq`, then checks if the message is still there. It passed once both sides had `durable: true` set with the same queue name. Along the way I also broke the consumer by accident — I had a typo, `eexport` instead of `export`, and the whole consumer container just kept crashing and restarting instead of connecting. That taught me a difference: a consumer that never connects looks a lot like "messages are getting lost," but it's actually a totally different problem (nothing is running at all vs. something is running but losing data).

**Publisher confirms.** `POST /publish` is supposed to only return 202 once RabbitMQ has actually confirmed it got the message. Before I got this right, I had a bug where every publish failed with the error `"content is not a buffer"`. What happened was I called `channel.publish(queueName, content, options)`, but the real function signature is `channel.publish(exchange, routingKey, content, options, callback)` — I forgot the exchange argument at the start, so everything after it shifted over by one spot, and RabbitMQ ended up trying to treat my options object as the actual message. Once I fixed that and added the confirm callback properly, I ran the real test (demonstration c): I published 5 messages using the fire-and-forget mode, then restarted the broker, and some of those messages were just gone — even though the HTTP request for each one had already gotten back a 202. Then I ran the same test using confirmed mode, and this time nothing was lost, even after the restart. That's the actual difference a 202 means or doesn't mean depending on the mode.

**Manual ack.** In `handleMessage`, I write the message to `received.jsonl` first, and only call `channel.ack()` after that write is done. If I did it the other way around — ack first, write second — and the consumer crashed in between those two lines, RabbitMQ would think the message was delivered and just forget about it, but it would never actually show up in the file. Writing first means the worst case is the message gets redelivered and maybe written twice, which is annoying but not silent data loss. I saw the other half of why manual ack matters in demonstration (b): I stopped the consumer, published a batch of messages, and they piled up in the queue instead of disappearing. When I started the consumer back up, it drained the whole backlog with nothing missing.

**correlationId.** The HTTP request can include an `X-Correlation-Id` header, or the producer makes one up if it's missing. Either way, it needs to end up as the AMQP message's `correlationId` property (not just somewhere in the JSON body), and the consumer needs to read it from `msg.properties.correlationId`, not from the message content. I actually checked this by looking at `data/received.jsonl` after running a test publish — the `correlationId` in the file matched exactly the `correlationId` the `/publish` response gave back, like `d1b071b3-f9d8-4ad2-8e69-13ef4ab3e6be`. If I'd put the id in the JSON body instead of the real AMQP property, that would probably still pass a casual look, but it's not actually using the mechanism RabbitMQ gives you for this.

## Decision

- `connectProducerChannel` connects to RabbitMQ, opens a **ConfirmChannel** (not a normal channel — you need this specific type to get publisher confirms at all), and declares the queue as `durable: true`.
- `publishMessage` turns the payload into a Buffer and sets the correlationId as a message property. In confirmed mode (the default), it sets `persistent: true` and doesn't resolve until the confirm callback fires — so the HTTP response literally waits on that. In fire-and-forget mode it skips both `persistent: true` and the wait, on purpose, because either one missing still leaves a real hole.
- `connectConsumerChannel` opens a normal channel, declares the same durable queue, and sets `channel.prefetch(1)` so it doesn't get handed a huge pile of unacked messages all at once.
- `handleMessage` reads `msg.properties.correlationId` and the message body, writes both (plus a timestamp) as one line to `received.jsonl`, and only acks after that write finishes.

## Alternatives considered

I want to be honest that I didn't start with the version above — I started with `channel.publish(queueName, content, options)`, missing the exchange argument. It looked correct, TypeScript didn't complain about it, and it only broke at runtime with a confusing error message. I switched to the correct signature because the problem wasn't one bad publish call, it was that I had the argument order wrong everywhere I called `publish()`.

I also thought about acking the message before writing it to the file, since that felt like the more "normal" order (do the thing, then mark it done). I didn't go with that because it makes the failure worse, not better — a crash between the two steps means the message is already gone from RabbitMQ's point of view but never made it into the file.

I considered just checking if `channel.publish()` returned `true` or `false` as my "did it work" signal, since a lot of basic examples online do that. I didn't use it because that return value is only about whether the local buffer on my machine is full — it has nothing to do with whether RabbitMQ actually received or saved the message, which is the whole point of what confirms are supposed to check.

## Consequences

Because the consumer only handles one message at a time (prefetch of 1, ack after writing), if the file it writes to gets slow, the whole queue backs up instead of messages getting skipped or lost — I think that's the right tradeoff for correctness here, but it would need to change if speed mattered more.

If two copies of the consumer ran at the same time against the same queue, RabbitMQ would just split messages between them, but both would be trying to write to the same `received.jsonl` file — I didn't build anything to handle that safely, so it could cause weird half-written lines. This assignment only runs one consumer, so I didn't deal with it, but it's a real gap.

The code doesn't put any limit on how big a message can be — a huge order (say, 100MB) would just get loaded fully into memory on both ends. It would still work, just slowly and wastefully.

If RabbitMQ's disk filled up completely, it stops accepting new messages rather than silently dropping them — so `/publish` would just hang until it times out and returns a 503, instead of lying and saying 202. That's better than losing data, but it does mean if the queue backs up in real life, checking disk space on the broker matters just as much as checking whether the consumer is alive.
