# ADR-002 — Correlation, idle timeout, partial results and deduplication in the order aggregator

**Status:** accepted
**Date:** 2026-10-06

## Context

Once the router splits an order into N messages, the items travel on three different queues, at different speeds, possibly out of order. The only thing that ties them back together is what each message carries, so the aggregator can only be as correct as the fields the splitter and the workers pass along. I also had to decide when an order is "finished" if a worker never answers, and what to do when RabbitMQ redelivers a result after a late ack. The obvious path was a counter per order, but a counter breaks on duplicates and gives no information about what is missing, so I chose a different structure.

## Decision

**Correlation.** In `route_order` every item message carries `orderId`, `correlationId` (the same value as `orderId`), `itemIndex` and `totalItems`. `totalItems` is the length of the original items array, so the aggregator never has to guess when an order is done. If a worker stripped or renamed `itemIndex` or `totalItems`, `aggregate_result` could not parse the result; it logs and acks it, so the order would end as a partial.

**Idle timeout.** The aggregator keeps `in_flight[orderId]` with a `last_seen` time that is reset every time a new distinct result arrives. A background thread, `sweep_timeouts`, wakes every second and publishes a partial for any order idle longer than `IDLE_TIMEOUT_SECONDS`. The value comes from `AGGREGATOR_IDLE_TIMEOUT_SECONDS` (5 s in docker-compose, which the tests assume). For production I would run 30 s. In this lab, a 50-item order completed with a 5 s idle timeout, so the gaps between results are far below 5 s, but I have only measured this lab, not a real warehouse or licensing system. A false partial is expensive for the consumer, who may retry an item that actually shipped, while waiting 30 s for a truly dead worker is cheap.

**Partial contents.** A partial message has `status: "partial"`, `receivedItems`, the `itemResults` collected so far, and `missingItemIndexes`, computed as `range(totalItems)` minus the received indexes. The consumer can retry exactly the missing items instead of re-processing the whole order.

**Duplicates.** Results are stored in `in_flight[orderId]["results"]` keyed by `itemIndex`, so a redelivered result finds its slot taken and is ignored. A duplicate does not reset `last_seen`, so a stream of redeliveries cannot keep an order open forever. Work is done under one lock, and publishing happens after the lock is released.

**Late results.** When an order is completed or timed out it is removed from `in_flight` and its ID goes into a `closed` dict with a 10-minute TTL. A result for a closed order is logged and ignored. This keeps the guarantee of exactly one message on `orders.complete` per order.

## Alternatives considered

- **Fixed deadline from the order's start.** Simpler, but a legitimate 50-item order could time out while every worker is healthy and still answering. An idle timeout measures silence, not total duration, so it scales with order size.
- **A counter per order instead of a dict keyed by `itemIndex`.** A redelivered duplicate would inflate the count, and a partial could not say which items are missing. Keying by index fixes both.
- **Emitting a second, corrected completion when a late result arrives after a partial.** More informative for the consumer, but it breaks "exactly one completion per order", and every consumer would have to handle updates. I rejected it and accept the cost described below.
- **Redis for the aggregation state.** It would survive an aggregator restart, but adds a service and a failure mode for a problem this size. I used an in-memory dict behind a lock.

## Consequences

- **State is in memory.** If the aggregator restarts mid-order, `in_flight` is lost and that order never gets a completion message. Redis or a persisted store would fix it.
- **An order that never gets any result is never timed out.** An entry is created only when the first result arrives. If every worker for an order is down, the aggregator never hears about it, so the "never hang" goal is not fully met in that case. Fixing it would mean registering the order with the aggregator when it is split.
- **Late results are discarded.** A consumer sees "partial" and never learns that the missing item finished moments later.
- **Cost of the `closed` dict.** It uses a small amount of memory per order for 10 minutes. Beyond that window, a very late duplicate would start a new entry and could eventually produce a second partial.
- **At 500 items or ten times the traffic,** I would look first at `publish_completion`, which opens a new RabbitMQ connection for every message, and at the single lock around all orders.
