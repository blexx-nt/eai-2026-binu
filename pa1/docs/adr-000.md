# ADR-000 — reading the legacy order file without breaking everything

**Status:** accepted
**Date:** 2026-09-14

## Context

The orders file (orders-20260901.txt) is not normal UTF-8 text, its CP1257.
At first when I just read the file normally with readFileSync and "utf8" it
didnt crash or give an error, it just quietly turned names like "Bērziņš"
into garbage with question marks and weird symbols. That was the scary part
- nothing tells you its wrong, it just looks wrong if you actually check it.

Also the customers.csv file is a totally different encoding (UTF-8) from the
orders file (CP1257). So in the same task I had two files with two different
encodings and I had to know which was which, nothing in the file tells you.

Other stuff that tripped me up:
- the amount field uses a comma instead of a dot for decimals, like "45,20".
  If I just used parseFloat on that it does weird stuff and can drop zeros,
  like "45,20" becomes 45.2 not 45.20, and thats wrong because its money.
- line 6 in the file is cut short (not the full 77 characters), so if I just
  sliced it like a normal line the program either crashes or gives wrong
  data without saying anything.
- there was also a negative amount in the file, which I almost thought was
  a mistake in the data, but its actually a refund, so I had to make sure I
  didnt accidentally filter it out.

## Decision

In ingest.ts I read the orders file as raw bytes (not as a string directly)
and then decoded it using TextDecoder with "windows-1257" so the Latvian
letters actually come out right. The customers.csv file I just read normally
as utf8 since that one was already fine.

For splitting lines I used a regex that handles both \n and \r\n line
endings, and I also removed the extra empty line at the end if the file had
one (because splitting on newline can leave one blank entry at the end).

For every line I check if its exactly 77 characters. If its not, instead of
crashing or skipping it silently, I push it into a "rejected" list with the
line number and a message saying why it was rejected. Then the loop just
keeps going to the next line.

For the actual fields I used .slice() with fixed column numbers instead of
splitting on spaces, because the customer names have spaces in them and that
would break everything.

For dates I just did string manipulation (splitting on the dots and putting
it back together as yyyy-mm-dd) instead of using new Date(), because Date
parsing is confusing with different formats and can mess up the day/month
order or add timezones we don't want.

For amount I only replaced the comma with a dot, I never turned it into an
actual number. I kept it as a string the whole time so nothing gets rounded
or loses zeros.

At the end I also check which customer IDs from the CSV never showed up in
any of the accepted orders, and put those into unmatchedCustomers.

## Alternatives considered

I thought about just using a library like iconv-lite to handle the
encoding instead of TextDecoder, but the assignment says not to use extra
dependencies, and also TextDecoder can already do it by itself so theres no
real reason to add another package.

I also thought about turning amount into a real number and just formatting
it nicely when I output it, but that defeats the point because the second
you turn "45,20" into a number you can lose the zero and theres no way to
get it back later. So keeping it a string the whole time is safer.

Another idea was to just throw an error when I hit the broken line 6 instead
of collecting it in rejected. But that seemed bad because then the entire
program stops and you lose all the good data too just because of one broken
line. Collecting it in "rejected" felt way better because you still get to
see everything else that worked.

If I had to keep this running for five years instead of just one week, I
wouldn't want to keep parsing this fixed-width file forever. What I'd
actually build is asking the other team to send the data as JSON instead,
with a proper schema (so every field has a name and a type, not just a
column position you have to guess). The cost of that is real though - it's
not free. I don't control their system, so they might just say no, or it
might take months to actually happen. Even if they agree, I'd probably need
to support BOTH formats for a while during the switch, so old files don't
suddenly break. And even a "new" JSON format could still change or break in
the future, so I'd want it to have some kind of version number in it so my
code can tell which version its reading. So its not a fix I can just do
myself right now, its more of a "this is what I'd push for if this was a
long term project."

## Consequences

Good thing: now the program doesn't crash on bad data, and money doesnt
quietly get corrupted from switching between comma and dot or from turning
it into a number. Nothing gets silently dropped either - every line ends up
somewhere, either in orders or in rejected.

Bad thing / what this gives up: this code is trusting that the file format
never changes. If the other system ever adds a new field in the middle of
the line, or someone has a name longer than 32 characters, my code won't
know - it'll just read the wrong columns into the wrong fields and keep
going like nothing happened, because it only checks the total line length,
not what's actually inside each column. Same thing if the file ever gets
saved as UTF-8 by accident instead of CP1257 - my code will still try to
decode it as CP1257 and just produce different wrong names, without any
error.

So basically the trade I made is: the code is simple and it works right now,
but it only works because I'm trusting the file format stays exactly the
same forever. That's the real cost of doing it this way instead of building
