# ADR-006 — Durable saga execution on Temporal

**Status:** accepted
**Date:** 2026-11-10

## Context

In PA6 the orchestrator held the saga in memory and wrote an in-progress record for each Idempotency-Key. To see what that costs, I started a checkout with shipping slowed to 2000 ms and ran `docker kill pa6-orchestrator` mid-saga. The client got no response at all (curl exit code 52, empty reply). When I sent the same request again with the same key, the orchestrator answered `409 idempotency_conflict`, "A request with this Idempotency-Key is still in progress". The record said the saga was running, but nothing was running it. Nothing would ever finish it, clear it, or refund a payment that had been taken, and no part of the system knew which steps had completed. The order was stuck.

A second problem appeared while porting: deciding which failures Temporal may retry. A 4xx from a mock (for example a declined payment) is a business refusal and will refuse again, so it must not be retried. A 5xx or no answer is temporary and may be retried.

## Decision

I ported the saga to Temporal and kept the behaviour the same: the same `POST /checkout`, the same four steps, the same compensation in reverse order, and the same responses.

The six HTTP calls are activities in `worker/src/activities/index.ts`. The workflow in `worker/src/workflows/checkout.ts` only sequences them and builds the result. It does no I/O and imports only types from the activities.

The retry policy is a `startToCloseTimeout` of 2500 ms, at most 3 attempts, an initial interval of 200 ms and a backoff coefficient of 2. A call that keeps timing out is tried three times in about 8 seconds, so it stays bounded instead of retrying forever.

An activity throws `ApplicationFailure.nonRetryable(message, code)` for a 4xx, using the mock's code. For a 5xx or no answer it throws a retryable error. A timeout is failed by Temporal itself.

If a step after payment fails for good, the workflow calls `releaseInventory` and then `refundPayment`. Shipping and notification have nothing to undo. The workflow never throws: it catches the `ActivityFailure`, reads its cause (a `TimeoutFailure` gives the code `timeout`, an `ApplicationFailure` gives its type as the code) and returns a `CheckoutResult` for every outcome. If a compensation fails, the result is `failed` with `compensation_failed`.

## Alternatives considered

The main alternative was to keep the PA6 orchestrator and add a recovery job that runs on startup and finishes stuck sagas. This is a real option, but it means rebuilding what Temporal already does. I would have to save the result of every step before moving on, scan for in-progress records on startup, work out which step to resume from, and make sure two instances do not resume the same saga at once. I would also need my own retry timers and a way to inspect stuck sagas. I rejected it because crash-safe recovery is exactly where hand-written code is most likely to have bugs that only appear during a crash.

I also considered retrying every failure and letting compensation sort it out. I rejected it because a declined payment would be tried three times for no reason, and the public test counts the attempts.

## Consequences

Crash recovery is now easier. In my crash test I killed the worker mid-saga and started it again. The workflow finished with `200 completed` and payment was authorized once, because Temporal had recorded its result in the history. Every attempt, failure and result is also visible in the Temporal UI, which PA6 never had.

Activities run at least once, not exactly once. In one crash run the shipping mock was called twice. The call that was in flight when the worker died did reach the mock, but Temporal cannot know that: it only sees that the attempt timed out, so it runs the activity again. No engine can avoid this, because it cannot tell "the request never arrived" from "it arrived and the reply was lost". If the step that ran twice had been `authorizePayment`, the customer could be charged twice. The fix is to pass an idempotency key, for example the orderId, to the payment service so a repeat is recognised and ignored. My mocks do not enforce this, so it is a risk I accepted for this exercise.

Costs I accepted:
- I now have to run and monitor a Temporal server and a worker, which PA6 did not need.
- Workflow code must be deterministic. I cannot use `fetch` or `process.env` in it, and a mistake there makes the workflow fail on every replay.
- Deploying a changed workflow while workflows are running can break their replay, so such changes need versioning or care.

## What the engine took over

- In-progress record and knowledge of completed steps: PA6 kept this in the orchestrator's memory and store, and a crash lost it, as the stuck 409 showed. In PA7 Temporal's workflow history records every step's result.
- Idempotency store and 409 logic: PA6 had its own code to store each key and answer replays, mismatches and conflicts. In PA7 the api starts the workflow with the Idempotency-Key as the workflowId, Temporal refuses a duplicate id, and the api reads the existing workflow to decide the answer. My PA7 code has no counterpart to this.
- Per-call timeouts: PA6 wrapped each downstream call in its own timeout and turned a connection abort into "timeout" by hand. In PA7 `startToCloseTimeout` does it, and the workflow sees a `TimeoutFailure`.
- Retry and crash recovery: PA6 had nothing that resumed a saga after a crash. In PA7 the retry policy handles temporary failures, and a restarted worker replays the history and continues from the step it was on.
